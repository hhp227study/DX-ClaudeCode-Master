## User Scenarios & Testing *(mandatory)*

### User Story 1 - 자기소개 등록 및 조회 (Priority: P1)

로그인한 사용자가 마이페이지에서 자신의 자기소개를 처음 작성해 저장하고, 이후 마이페이지에 다시 방문했을 때 저장한 자기소개가 그대로 표시된다.

**Why this priority**: 이 기능의 핵심 가치. 자기소개를 저장하고 다시 볼 수 없다면 기능 자체가 성립하지 않는다. 이 스토리만 구현해도 사용자에게 의미 있는 MVP가 된다.

**Independent Test**: 자기소개가 비어 있는 계정으로 로그인 → 마이페이지에서 자기소개 입력 후 저장 → 페이지 새로고침(또는 재로그인) 후 마이페이지에서 동일한 내용이 표시되는지 확인.

**Acceptance Scenarios**:

1. **Given** 자기소개를 등록한 적 없는 로그인 사용자가 마이페이지에 있을 때, **When** 자기소개 입력란에 내용을 작성하고 저장하면, **Then** 저장 완료 피드백이 표시되고 입력한 내용이 유지된다.
2. **Given** 자기소개를 저장한 사용자가, **When** 페이지를 새로고침하거나 재로그인 후 마이페이지에 진입하면, **Then** 저장했던 자기소개가 입력란에 그대로 표시된다.
3. **Given** 자기소개를 등록한 적 없는 사용자가 마이페이지에 진입하면, **When** 자기소개 영역을 보면, **Then** 빈 입력란과 작성을 유도하는 안내 문구가 표시된다.

---

### User Story 2 - 자기소개 수정 (Priority: P2)

이미 자기소개를 등록한 사용자가 마이페이지에서 기존 내용을 고쳐 저장하면, 이후 조회 시 수정된 내용이 표시된다.

**Why this priority**: 등록·조회가 가능해진 뒤 자연스럽게 필요한 다음 단계. 등록과 동일한 저장 흐름을 재사용하므로 P1 위에 얹는 증분이다.

**Independent Test**: 자기소개가 이미 저장된 계정으로 로그인 → 마이페이지에서 내용 수정 후 저장 → 새로고침 후 수정된 내용이 표시되는지 확인.

**Acceptance Scenarios**:

1. **Given** 자기소개가 저장돼 있는 사용자가 마이페이지에 있을 때, **When** 기존 내용을 수정하고 저장하면, **Then** 저장 완료 피드백이 표시되고 이후 조회 시 수정된 내용이 표시된다.
2. **Given** 사용자가 자기소개를 수정하던 중, **When** 저장이 실패하면(예: 네트워크 오류), **Then** 오류 안내가 표시되고 작성 중이던 내용은 사라지지 않는다.

---

### User Story 3 - 자기소개 비우기 (Priority: P3)

자기소개를 더 이상 노출하고 싶지 않은 사용자가 내용을 모두 지우고 저장하면, 자기소개가 등록 전 상태(빈 상태)로 돌아간다.

**Why this priority**: 사용 빈도는 낮지만 자기 정보에 대한 통제권을 완성하는 마무리 단계. 수정 흐름의 특수 케이스로 구현 부담이 작다.

**Independent Test**: 자기소개가 저장된 계정으로 로그인 → 입력란을 모두 비우고 저장 → 새로고침 후 빈 입력란과 안내 문구가 표시되는지 확인.

**Acceptance Scenarios**:

1. **Given** 자기소개가 저장돼 있는 사용자가, **When** 입력란을 모두 비우고 저장하면, **Then** 저장이 정상 처리되고 이후 조회 시 등록 전과 동일한 빈 상태로 표시된다.

---

### Edge Cases

- 공백(스페이스·줄바꿈)만 입력하고 저장하면? → 빈 값 저장과 동일하게 "자기소개 없음" 상태로 처리한다.
- 최대 길이(500자)를 초과해 입력하면? → 초과 입력을 막거나 저장 전에 초과 사실을 안내하고 저장을 차단한다.
- 저장 도중 네트워크·서버 오류가 발생하면? → 오류 메시지를 표시하고 작성 중이던 내용을 보존한다. 기존 저장값도 훼손되지 않는다.
- 프로필 정보가 늦게 로드되는 동안 사용자가 입력란을 보면? → 로드 완료 시 저장된 값으로 동기화된다(기존 별명 입력란과 동일한 동작).
- 여러 줄로 작성된 자기소개는? → 줄바꿈이 유지된 상태로 저장·표시된다.
- 별명 저장과 자기소개 저장을 연달아 수행하면? → 각 저장이 서로의 값을 덮어쓰거나 훼손하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 마이페이지에 자기소개 항목이 별명과 동일한 인라인 편집 방식(항상 편집 가능한 여러 줄 입력란 + 저장 버튼)으로 표시되어야 하며, 저장된 자기소개가 있으면 입력란에 그 내용을, 없으면 작성을 유도하는 안내 문구를 보여줘야 한다. 별도의 조회/편집 모드 전환은 두지 않는다.
- **FR-002**: 로그인한 사용자는 마이페이지에서 자기소개를 새로 등록할 수 있어야 한다.
- **FR-003**: 로그인한 사용자는 이미 등록된 자기소개를 수정할 수 있어야 한다.
- **FR-004**: 저장된 자기소개는 새로고침·재로그인·다른 기기 접속 후에도 동일하게 조회되어야 한다(계정 단위 영구 저장).
- **FR-005**: 자기소개는 여러 줄 입력을 지원해야 하며, 저장·조회 시 줄바꿈이 유지되어야 한다.
- **FR-006**: 자기소개는 최대 500자까지 허용하며, 초과 시 저장 전에 사용자에게 알리고 저장을 막아야 한다.
- **FR-007**: 빈 값 또는 공백만으로 저장하면 자기소개가 없는 상태로 처리되어야 한다(자기소개 비우기).
- **FR-008**: 저장 성공 시 완료 피드백을, 실패 시 오류 안내를 표시해야 하며 실패 시 작성 중이던 내용이 사라지면 안 된다.
- **FR-009**: 자기소개는 본인만 조회·등록·수정할 수 있어야 한다.
- **FR-010**: 기존 별명 변경, 프로필 이미지, 로그아웃 등 마이페이지의 기존 기능은 변경 없이 그대로 동작해야 한다.
- **FR-011**: 이미 정의되어 있는 데이터 저장 구조(테이블·컬럼)를 변경하지 않고 구현해야 한다. 새 테이블 생성, 기존 테이블의 컬럼 추가·삭제·변경은 허용되지 않는다.

### Key Entities

- **프로필(Profile)**: 사용자당 1개 존재하는 개인 정보 묶음. 별명(name)과 자기소개(introduction)를 보유한다. 자기소개는 선택 항목(비어 있을 수 있음)이며, 기존 구조에 이미 자기소개 저장 항목이 마련되어 있으므로 구조 변경 없이 사용한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자가 마이페이지 진입부터 자기소개 등록 완료까지 30초 이내에 마칠 수 있다.
- **SC-002**: 저장된 자기소개가 새로고침·재로그인 후 조회했을 때 100% 동일하게 표시된다.
- **SC-003**: 저장 시도 후 2초 이내에 성공 또는 실패 피드백이 표시된다.
- **SC-004**: 기존 마이페이지 기능(별명 변경, 프로필 이미지, 로그아웃)이 기능 추가 전과 동일하게 동작한다(회귀 0건).
- **SC-005**: 데이터 저장 구조 변경 0건으로 기능이 완성된다.

## Assumptions

- 자기소개의 "조회"는 본인 마이페이지에서 자신의 자기소개를 확인하는 것을 의미한다. 이 앱에는 다른 사용자의 프로필을 열람하는 화면이 없으므로 타인 프로필 조회는 범위 밖이다.
- 기존 프로필 데이터 구조에 자기소개를 저장할 항목이 이미 마련되어 있어, 구조 변경 없이 기능 구현이 가능하다.
- 빈 값(공백 포함) 저장은 "자기소개 삭제"와 동일하게 취급한다. 별도의 삭제 버튼은 요구되지 않았다.
- 서식(굵게, 링크 등)은 지원하지 않는 일반 텍스트이며, 줄바꿈만 유지한다.
- 기존 별명 저장과 동일한 인증 체계(로그인된 본인 계정)를 재사용한다.
